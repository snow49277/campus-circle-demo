# 校园互助平台：产品定义与 Demo 范围

版本：v0.1  
日期：2026-10-17  
状态：讨论记录与范围草案；不是已验证的市场结论或完整 PRD。产品名称待定。

## 1. 产品定义

面向同一所大学的学生，让个人积累的经验与技能成为获取他人帮助的资源。通过直接互换、多人互助环和跨时间的贡献记录，连接用户能提供的帮助与当前需求。

核心价值主张：提供一次双方认可的帮助，获得一次接受帮助的机会。平台不根据技能、身份、时长或难度设置兑换倍率。

## 2. 用户已确认的原则

- 首批服务对象限定在同一所大学。
- 一次帮助换一次帮助，不按贡献量给不同帮助定价。
- 支持多人循环，例如 A 帮 B、B 帮 C、C 帮 A。
- 同时容纳一次性问题和持续学习关系；持续关系需双方自愿续约。
- 环发生变化时，尽量保留双方愿意继续的帮助关系，为其他需求重新匹配；不保证一定能补齐。
- 同校身份、具体经历与作品、其他同学反馈均可查看，也可选择先聊几句。
- 允许暂时没有需求的人继续提供帮助，并记录尚未获得回报的贡献。
- 允许先获得一次帮助；这次帮助尚未通过付出抵偿时，必须先帮助别人才能再次获得帮助。
- 上述限制只影响再次接受帮助；浏览、沟通、匹配和提供帮助仍然可用。
- 可以帮助其他同学，无需回报原帮助者。

## 3. 已讨论的履约规则

- 双方在开始前确认本次帮助的内容、范围、形式和时间。
- 发布或承诺帮助不计为完成；实际完成并经接受者确认后记录贡献，分歧进入争议处理。
- 已完成的贡献不因环中其他人退出而失效。
- 取消或未实际发生的帮助不计入已完成次数；预约取消后释放对应资格。
- 接受预约时需占用对应互助机会；没有提前贡献的用户只能占用一个先接受帮助的名额，防止并发预约绕过限制。
- 有既往贡献时，接受帮助先使用已有机会；不能把已经获得回报的贡献重复记录为新的机会。
- 贡献记录表示未来求助资格，不代表平台保证立即找到帮助者。
- 长期学习由双方约定具体阶段，确认下一次内容后再继续；不自动按时长切分或强制续约。

## 4. 第一版 Demo 建议范围（实施默认方案，尚未验证）

使用一个明确标注为虚构的校园、虚构人物和示例作品，不冒充真实身份验证或真实用户反馈。

| 模块 | 展示内容 |
| --- | --- |
| 校园互助首页 | 可提供的帮助、当前需求、发布入口 |
| 互助名片 | 同校状态、经历、作品、历史反馈 |
| 发布帮助与需求 | 具体内容、形式、可用时间、一次性或持续意向 |
| 匹配建议 | 优先演示两人互换与三人环；清楚说明匹配原因 |
| 沟通与约定 | 可选沟通、修改范围、接受或拒绝、预约 |
| 我的互助 | 待确认、待进行、待完成确认、已完成、已取消、争议状态 |
| 反馈与继续互助 | 留下反馈、再次约定、查看未获得回报的贡献 |

匹配实现建议：先用可解释的条件匹配验证流程，依据同校、供需类别、形式和时间等条件找候选，再让当事人确认。页面上区分“找到候选环”与“全员确认成立”，不将预设演示结果宣传为成熟的自动匹配能力。

第一版不优先实现：跨校、现金交易、帮助价格、贡献排行榜、大规模推荐算法、真实校园身份接入和生产级即时通信。完整产品 PRD 仍需描述必要的隐私、举报和争议处理规则；网页中未接入的能力必须标注为演示。

## 5. 必须演示的场景

1. 三人环成功：发布供需 → 匹配候选 → 可选沟通 → 全员确认 → 分别履约 → 反馈。
2. 先接受后付出：首次获得帮助 → 再次求助受限 → 帮助他人并确认完成 → 恢复资格。
3. 成员退出：保留已完成贡献和仍有效的约定 → 取消关联的未完成安排 → 尝试补充匹配 → 无结果时展示等待状态。
4. 持续关系：一期结束 → 双方自愿续约 → 提供者暂时没有需求仍继续帮助 → 新完成的、未获得回报的贡献被记录。
5. 无匹配与拒绝：解释没有候选或尚未全员确认 → 调整需求或继续等待，不虚构匹配成功。

## 6. 后续研究与待确定事项

- 竞品研究：调查校园互助、技能交换和时间互助等相关方案；区分已核实功能、推断和我们的设计选择，记录来源及查询日期。
- 需求验证：学生是否愿意提供帮助、哪些需求最常见、一次换一次是否被双方认可。
- 供需验证：同校是否有足够匹配密度；多人环是否比直接互换增加实际完成的互助。
- 履约细则：确认期限、失联、爽约、争议、申诉以及恶意刷互助的处理。
- 隐私与信任：身份验证方式、资料可见范围、作品授权和反馈展示规则。
- 持续学习：如何界定一次约定，避免无限承诺和强制续约。
- 实现边界：哪些能力使用本地模拟，哪些需要真实后端；公开 Demo 不应接收真实敏感资料。
- 发布信息：产品名称、校园展示方式、GitHub 仓库归属与仓库名、在线部署方式。

## 7. 交付顺序

1. 产品定义与范围：本文件。
2. 竞品分析：有来源的比较，重点服务于匹配、信任、互助规则和履约设计。
3. PRD 与流程：角色、页面、状态、权限、异常分支、验收标准。
4. 网页 Demo：实现核心路径与明确的演示数据，验证交互和关键规则。
5. 公开展示材料：README、截图、操作说明、设计取舍、已知限制、后续计划。
6. GitHub 与在线体验：准备可公开的仓库内容，确认发布目标后上传；单独配置网页访问地址并验证可访问性。

## 8. Demo 完成标准

- 访客可完整体验至少一轮三人互助，不只浏览静态页面。
- 先接受帮助的限制与解除可以实际操作验证，多个预约不能绕过限制。
- 退出不会清空已完成贡献；匹配失败具有明确状态。
- 一次性与持续帮助都能通过清楚的约定展示。
- 虚构数据、模拟能力与尚未实现的功能清楚标识。
- PRD、竞品分析、网页行为与项目说明一致。
- 公开仓库不包含凭证和个人隐私；README 提供运行说明与实际可访问的体验入口。
