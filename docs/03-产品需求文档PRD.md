# 校园互助平台 PRD

版本：v0.1｜日期：2026-10-17｜状态：可用于原型设计的初稿，未进入生产上线

## 1. 产品目标与定位

帮助同一所大学的学生将自己的经验和技能转化为获取他人帮助的机会。一次双方认可并完成的帮助，对应一次接受帮助的机会；不按时长、技能、专业或身份估价。

首版验证三个问题：用户能否表达具体供需；是否理解并愿意参加多人互助环；能否在有人退出后仍正确保留贡献和履约状态。

本 PRD 中“已确认原则”来自产品讨论；具体页面、时间参数和技术约束属于首版设计建议，可通过后续体验调整。没有声称已完成用户研究。

## 2. 用户、角色与权限

同一名学生既可提供帮助，也可接受帮助，不设置永久的老师与学生身份。

| 角色或状态 | 权限 |
| --- | --- |
| 公开 Demo 访客 | 浏览虚构案例，进入演示身份，切换场景；不能看到真实学生资料 |
| 同校已验证成员（Demo 中模拟） | 发布供需、查看校内名片、可选沟通、确认约定 |
| 有一次尚未抵偿的接受记录 | 保留浏览、沟通、发布和提供帮助权限；不能新增接受帮助的预约 |
| 约定提供者 | 编辑待确认内容、确认预约、请求取消、提交已完成 |
| 约定接受者 | 确认预约、确认完成、提出争议、留下反馈 |
| 演示操作面板 | 明示模拟其他成员操作及争议处理；不伪装成真实他人回复或平台人工服务 |

真实产品中未验证者不得进入校内私密资料与交易流程；真实身份认证不在首版接入范围。

## 3. 范围与优先级

### P0：必须可操作

- 虚构校园身份与互助名片：经历、作品示例、已完成约定对应的反馈。
- 发布帮助和需求；编辑、暂停；一次性或持续意向。
- 基于示例数据与用户输入的条件匹配：两人互换、三人环、无结果。
- 匹配原因、环中角色、全员确认与拒绝。
- 可选的本地演示对话与约定确认。
- 接受资格占用、完成确认、贡献记录、取消与退出。
- 一期后双方自愿续约、保留尚未获得回报的贡献。
- 空状态、受限状态、争议待处理状态、场景重置与本地保存。

### P1：后续扩展

更大规模环、真实用户登录、实时消息、校园认证、通知、运营审核后台和匹配优化。

### 非目标

现金交易、技能报价、付费购买机会、贡献榜、强制长期教学、自动保证学习成果。首版不提供专业医疗、法律等服务的资质判断；经历分享应写明范围，不替代专业资格。

## 4. 信息架构与页面要求

| 页面 | 核心内容与操作 | 必须覆盖的状态 |
| --- | --- | --- |
| 校园广场 | 我能提供／我需要；分类、形式、时间筛选；查看详情；发布入口 | 有结果、筛选无结果、首次空白 |
| 互助名片 | 同校状态、相关经历、作品、文字反馈；先聊聊／发出邀请 | 新用户无评价、无作品、资料为本人描述 |
| 发布表单 | 类型、类别、标题、具体范围、形式、可用时间、一次或持续意向 | 必填错误、保存成功、编辑失效匹配提示 |
| 匹配页 | 我帮助谁／谁帮助我；可查看完整环；匹配依据；确认或拒绝 | 候选、部分确认、成立、过期或失效、无结果 |
| 对话与约定 | 本地演示消息、约定版本、范围、形式、时间、双方确认 | 待对方确认、修改后重新确认、取消协商 |
| 我的互助 | 我提供的／我接受的；状态、下一步按钮；贡献记录 | 待进行、待确认完成、争议、取消、完成 |
| 关系详情 | 已完成期次、当前约定、再次邀请 | 续约待确认、继续、不再继续 |

浏览器刷新保留本地演示状态；“重置演示”明确告知会清除本地输入并要求确认。公开 Demo 不索取真实学号、密码、证件或联系方式。

## 5. 发布与约定

发布条目至少包含：供给或需求、标题、类别、具体内容、线上／线下形式、可用时间。持续意向只表达希望继续，不一次性预订所有未来阶段。

双方确认的每份约定包含：提供者、接受者、对应供需条目、帮助目标与边界、双方准备事项、形式、开始与结束时间。预计时长只用于安排，不产生兑换倍率。

例如：“一起检查预算 6000 元、用于剪辑的配置单，讨论兼容性和取舍；不负责采购或安装。”本例预算属于待讨论的电脑用途条件，不是帮助费用。

确认后的内容修改生成新版本并要求双方重新确认。新版本确认前保留原约定；不得悄悄扩大范围或挪动已预约时间。类别吻合不代表一定满足需求，当事人始终可拒绝。

## 6. 次数与资格规则

### 6.1 基础约束

设 G 为已确认提供次数，H 为已确认接受次数，R 为已占用但尚未完成／取消的接受预约数，B = G − H。

- 初始 G=H=R=0。每一次帮助只有提供者和接受者各一名。
- 接受预约的条件：B − R ≥ 0；成功后 R 增加 1。
- 因此 B − R 始终不低于 −1，表示最多存在一次没有既往贡献覆盖的接受预约或已接受帮助。
- 不能把未来承诺提供的帮助计入 G；只有实际完成才解锁新的资格。
- 本轮的贡献先抵偿已经接受的帮助；B 为正时才表示尚未获得回报的贡献。
- 预约取消使 R 减少 1，不更改 G、H；确认完成使接受者 H 加 1、R 减 1，同时提供者 G 加 1。
- UI 分开展示“尚未获得回报的贡献”“已预约”“是否可先接受一次”，不把初始机会写成已经贡献所得。

| 示例 | G | H | R | 能否再预约接受一次 |
| --- | --- | --- | --- | --- |
| 新用户 | 0 | 0 | 0 | 可以 |
| 新用户已预约一次 | 0 | 0 | 1 | 不可以 |
| 先接受已完成，尚未帮助别人 | 0 | 1 | 0 | 不可以 |
| 此后帮助别人一次 | 1 | 1 | 0 | 可以 |
| 提前帮助两次，已有两次接受预约 | 2 | 0 | 2 | 可以再占用一次先接受名额，此后不能新增 |

以上按“最多一次尚未抵偿”解释，适用于每轮往来，不是赠送可累加的新手额度。UI 使用“接下来轮到你帮助一位同学”，不使用债务金额或价格语言。

### 6.2 一致性

同一约定只能确认完成一次；双方次数变化必须一起生效。重复点击、刷新重试和重复消息不得重复入账。自助交易禁止；更换演示身份不得改变底层同一用户的记录。

环成立时统一检查所有接受者的资格、条目可用性与时间冲突，并一次性创建预约占用。任一检查失败则不建立任何新预约，保留可解释的失效原因。早期意向确认不占额度，页面明示“尚未预约成功”，最终成立时必须重新校验。

本地 Demo 只能验证单浏览器中的一致性逻辑。真实产品必须由服务端认证与事务保证，不能依赖客户端存储防作弊。

## 7. 匹配规则

1. 过滤同校、未暂停、身份有效的条目；排除本人、已满足需求及无法新增接受预约的需求方。
2. 供给类别匹配需求类别，形式相容，能提出共同可用的时间段，再形成候选帮助边。细节适配由用户确认。
3. 搜索两个或三个不同用户组成的闭环；每个用户在该候选环中提供一次、接受一次，不重复占同一需求。
4. 每条边分别约时间，不要求全环同时进行；同一人不同约定的时间不得冲突。
5. 依据明确条件展示匹配原因，优先较短环，同条件按需求等待时间与稳定 ID 排序；不按贡献次数、专业身价或热门程度排名。
6. 成员分别接受自己参与的约定；所有人确认当前版本后才尝试建立整环。
7. 条目变化、资格改变或成员拒绝使候选失效；展示原因并重新搜索，不自动替用户同意。

无环时可展示单向帮助候选：接受者仍须有资格，提供者须明示愿意本次不即时获得回报。提供者完成后仍获得贡献记录。找不到供给时可调整类别、形式或时间，也可保留需求等待；不得生成虚假成功结果。

首版以规则搜索为实现建议，不使用无法解释的“AI 精准匹配”文案。

## 8. 生命周期与异常处理

| 状态 | 可发生的操作 | 次数／预约处理 |
| --- | --- | --- |
| 草案／候选 | 编辑、沟通、接受意向、拒绝 | 无完成次数、无预约占用 |
| 已约定 | 查看时间、开始、请求取消 | 接受者占用 1 次 |
| 进行中 | 提供者提交完成、请求取消或提出争议 | 保持占用 |
| 待确认完成 | 接受者确认或提出争议 | 保持占用，不自动记完成 |
| 已完成 | 评价、邀请下一期 | 双方次数一次性更新，释放该占用 |
| 取消待确认 | 对方确认或提出争议 | 保持占用 |
| 已取消 | 重新发布或匹配 | 释放占用，不改变已完成记录 |
| 争议处理中 | 查看事实、补充说明、演示处理结果 | 冻结本约定结算，不冻结其他无关能力 |

拟定默认参数：候选邀请 48 小时未全员确认即失效；提交完成 48 小时未回应显示提醒和争议入口，不自动判定完成或取消。参数为设计建议，Demo 提供“模拟超时”操作，不要求访客等待。

开始前取消立即生效并通知相关成员；已经开始或提交完成后需要双方协商，无法一致则进入争议。Demo 的处理面板明确模拟“确认已完成”或“确认未发生并取消”，均记录原因，不提供真实人工仲裁承诺。

### 环断裂与重新匹配

- 环是协调视图，每条帮助有独立的约定和结算状态。
- 退出环不撤销已完成贡献，也不默认取消所有人的帮助。
- 对退出成员参与的未开始安排明确取消并释放资格；已开始的约定遵循协商或争议规则。
- 其他关系由参与双方选择继续或取消，不将失去回报的一方强制留在环内。
- 已付出者重新求助时使用保留记录，无需为了“重新闭环”再提供一次。
- 新成员加入形成新版本，相关当事人重新确认；历史已完成边只展示历史，不重新计账。
- 首版修复可退化为符合资格的单向替补，不保证每次都形成新闭环；必须如实显示“部分恢复”或“等待匹配”。

### 持续关系

每一期单独约定、占用和完成。保留关系不等于保留未来接受资格。提供者暂无需求仍可继续帮助；接受者每一期都要满足次数规则，否则应先帮助别人。双方私下自愿交流无需在平台反复结算，平台不计入未登记、未确认的交流。

## 9. 信任、反馈与资料范围

- 同校验证只证明学校身份；经历标注本人描述，作品为展示材料，不作能力担保。
- 默认校内可见，校外公开页仅展示产品介绍和虚构 Demo。具体约定与私聊仅相关双方可见；环成员只看到协调所需的状态，不看到其他边的私聊。
- 仅已完成约定的参与者可留下对应反馈，每人每份约定一条；内容聚焦履约、沟通和帮助内容。首版不做综合星级和排行榜。
- 提供举报入口，可针对资料、对话或约定；拉黑后不产生新邀请，已有约定仍需按取消或争议流程处理。
- 不公开学号、校园邮箱验证凭证、精确宿舍信息。真实校园认证与审核流程在真实试点前另行验证。
- 刷贡献不能仅靠算法解决：真实产品需能发现重复协同行为并进行审核；不把熟人重复互助一律判为作弊。首版只验证自助交易、重复结算和资格限制。

## 10. 核心数据对象

| 对象 | 必要字段 |
| --- | --- |
| User | id、campusId、displayName、verificationStatus、bio、experiences、works |
| Listing | id、ownerId、offer/request、category、scope、mode、availability、ongoingIntent、status、version |
| Agreement | id、providerId、receiverId、offerId、requestId、scope、time、mode、status、version、confirmation、cancellationReason |
| Circle | id、agreementIds、version、memberAcceptances、status、previousCircleId |
| Reservation | agreementId、receiverId、active/released/settled；每个约定唯一 |
| ContributionEvent | agreementId、providerId、receiverId、confirmedAt；每个完成约定唯一 |
| Relationship | providerId、receiverId、historyAgreementIds、renewalIntent；不自动创建未来预约 |
| Review / Message / Report | 作者、关联对象、内容、时间、状态；消息与举报有访问边界 |

G、H 从唯一完成事件推导，R 从有效预约推导，避免 UI 随意直接增减余额。后端实现时的接口与数据库选型待技术方案确定。

## 11. 交互质量与可访问性

桌面与手机均能完成核心路径。环图同时提供文字列表，不单靠颜色区分状态。表单有可读标签和具体错误提示；按钮可用键盘操作；弹窗有焦点管理。受限操作解释原因并给出可执行入口。

演示身份、虚构资料、模拟消息和管理操作持续可识别；不显示伪造的“在线人数”“已验证真实身份”或真实履约数据。

## 12. 验收与验证计划

详细脚本见 [流程与验收](04-用户流程与验收.md)。P0 发布门槛：三人环从发布到反馈完整可操作；先接受限制、并发占用、重复完成、退出保留贡献和续约资格均通过检查。

未来试点建议关注：供需发布完成率、获得有效候选比例、全员接受率、约定完成率、等待时间、先接受者后续付出比例、再次互助比例、取消与争议原因。每个指标按对应状态与唯一用户／约定计数，Demo 不填造实际结果，不预设未经验证的增长目标。
